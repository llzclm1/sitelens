# SiteLens 产品需求文档

> 版本：1.0
> 日期：2026-08-10
> 作者：Codex 协助生成
> 状态：设计审查通过；V1 已部分实现，进入支付回归与真实用户验证

这份 PRD 定义 SiteLens 第一阶段要验证的用户价值、付费路径和产品边界，避免在真实购买发生前扩展成大型营销平台。

---

## 1. 产品概述

### 1.1 一句话定位

SiteLens 是一个面向创业者和小企业主的自助式网站增长诊断工具：用户提交公开网站 URL，系统根据页面证据找出最值得先改的转化问题，并给出可执行的文案和页面结构建议。

第一阶段优先优化 SaaS 首页的注册和 Demo 转化，但产品入口不拒绝其他公开网站。

### 1.2 核心价值主张

SiteLens 帮助有公开 SaaS 首页、但注册或 Demo 转化不足的创业者，根据首页真实内容找出最值得先改的增长问题，并提供有证据的文案和页面结构建议，让用户知道下一步该改什么。

SiteLens 卖的不是 AI 分数，而是：

```text
Website data
  → Analysis framework
  → Page evidence
  → Business insight
  → Prioritized action plan
```

### 1.3 产品边界

V1 做：

- 公开首页 URL 分析。
- 网站目标和目标用户上下文收集。
- HTML、Meta、标题、CTA、信任元素、结构、Schema 和截图证据提取。
- Evidence Report、优先行动计划、文案与首页结构改写。
- 一次性 Deep Growth Report 购买和解锁。

V1 不做：

- 自动修改用户网站。
- 完整全站 SEO SaaS。
- 无来源的行业 Benchmark。
- 企业级权限、多站点和白标工作区。
- 保证转化率提升或“10 倍增长”。

## 2. 背景与目标

### 2.1 市场背景

“输入 URL、得到评分和建议”已经是成熟的产品表达。现有直接产品已经覆盖截图、页面评分、问题优先级、改写、基准比较和一次性报告，单独宣传“AI 网站分析”不足以形成差异。已有扫描记录见 [`research/competitor-scan.md`](../research/competitor-scan.md)。

相邻产品分别占据不同位置：Unbounce 更强调 AI 文案、A/B 测试和流量优化；Hotjar 更强调录屏、行为数据与 AI 洞察；Semrush 把技术 SEO、竞品比较和 AI 搜索可见度放在大型营销套件中。[Unbounce 功能页](https://unbounce.com/product/features/)、[Hotjar 说明](https://help.hotjar.com/hc/en-us/articles/36820019634961-What-is-Hotjar)、[Semrush AI Visibility](https://www.semrush.com/kb/1626-ai-visibility-features)

SiteLens 的机会不在于覆盖更多指标，而在于把创业者真正关心的问题讲清楚：页面具体哪里不清楚、为什么会影响注册或询盘、先改什么、可以怎么改。

本 PRD 不使用未经验证的市场规模、行业平均分或转化提升数字。第一阶段以真实提交、报告反馈和付费行为验证机会。

### 2.2 产品目标

**O1：验证用户是否愿意为“告诉我网站为什么不转化，并告诉我怎么改”付费。**

- KR1：30 天完成 1,000 次网站分析、收集 100 个邮箱、获得 10 个付费用户。以上是验证目标，不是市场预测。
- KR2：完成 5–10 个真实 Indie Hacker / 小 SaaS 用户的人工报告质量复核。
- KR3：建立完整漏斗：访问、提交、完成、查看报告、留邮箱、开始支付、支付成功、打开深度报告。
- KR4：确认用户认为报告“具体、可信、可执行”，人工评分目标为 4/5 左右；该目标需在首批样本后校准。

### 2.3 成功指标

- **北极星指标**：被用户打开的已完成 Deep Growth Report 数量。
- 辅助指标：
  - 首页访问 → URL 提交率。
  - URL 提交 → 分析完成率。
  - 免费报告查看 → 邮箱提交率。
  - 免费报告查看 → 付费开始率和付费成功率。
  - 付费报告的打开率和用户评分。

## 3. 用户画像

### 画像 1：Indie Hacker / 小型 SaaS 创业者

- **基本信息**：个人创始人或小团队，通常自己负责产品、开发和营销。
- **典型场景**：产品已经上线，有公开首页和一些访问，但注册、试用或 Demo 不足。
- **核心任务（JTBD）**：JTBD-1、JTBD-2、JTBD-3。
- **当前痛点**：能看出网站效果不好，却无法判断问题是定位、文案、信任、CTA 还是页面结构；通常只能问朋友、发社区或阅读泛泛的营销文章。
- **第一优先级**：P0，是首页主叙事和默认分析场景。

### 画像 2：小企业主

- **基本信息**：有官网和获客需求，但缺少 SEO、转化和内容判断能力。
- **典型场景**：网站已经投入成本，但没有带来足够的询盘、预约或电话。
- **核心任务（JTBD）**：JTBD-1、JTBD-2。
- **当前痛点**：很难把“网站没有客户”拆解成可执行的页面问题。
- **第一优先级**：P1，使用相同核心流程，通过网站目标选项适配获客和预约场景。

### 画像 3：设计师 / 营销人员

- **基本信息**：需要快速评估客户网站，或在提案和改版前形成结构化意见。
- **典型场景**：短时间内需要一份有证据的初步诊断。
- **核心任务（JTBD）**：JTBD-2、JTBD-3。
- **当前痛点**：人工评估耗时，现有自动工具常常偏技术或缺少可交付的改写建议。
- **第一优先级**：P2，后续通过多站点和白标报告扩展。

## 4. 需求分析

### 4.1 JTBD 清单

| ID | 核心任务 | 优先级 | 对应用户画像 |
|---|---|---|---|
| JTBD-1 | 当我的网站有访问但没有注册或询盘时，我想知道最影响转化的前三个具体问题，以及页面上的证据。 | P0 | 画像1、画像2 |
| JTBD-2 | 当我准备修改首页时，我想得到可以直接执行的文案、结构和 CTA 改动，而不是泛泛的营销建议。 | P0 | 画像1、画像2、画像3 |
| JTBD-3 | 当我考虑是否为网站诊断付费时，我想看到分析依据、影响解释、方法边界和明确的行动优先级。 | P0 | 画像1、画像3 |

### 4.2 需求来源追溯

- 原始项目书：定义网站定位、分析维度、免费与付费报告和商业验证目标。
- 竞品扫描：发现 URL 分析、评分、截图和改写已经普遍存在，因此需要证据优先和更窄的首要场景。
- 信任体系设计：要求 Growth Framework、Evidence Layer、透明分析过程和明确边界。
- 技术评审：确认 URL 抓取、SSRF 防护、视觉模型、支付校验和报告交付必须作为产品边界的一部分。
- 设计审查：补充方向性评分、目标必选、支付幂等、未知信息和邮箱用途说明。

## 6. 产品架构

### 6.1 功能模块划分

| 模块 ID | 模块名称 | 包含功能 | 职责描述 |
|---|---|---|---|
| M-1 | 分析入口 | F-1 | 收集网站 URL、网站目标和目标用户，完成基础校验并创建分析请求。 |
| M-2 | 页面证据引擎 | F-2 | 抓取公开首页并产出结构化页面证据。 |
| M-3 | 报告与行动计划 | F-3、F-4、F-5 | 将证据转成问题、影响、改法和可执行行动。 |
| M-4 | 信任与报告交付 | F-6、F-12 | 解释分析方法、边界、未知信息，并管理报告保存和邮箱交付。 |
| M-5 | 付费报告 | F-11、F-12 | 创建支付请求、接收支付确认并解锁 Deep Growth Report。 |

### 6.2 模块关系

- M-1 → M-2：用户提交上下文后开始页面证据采集。
- M-2 → M-3：结构化证据进入报告生成。
- M-3 → M-4：报告展示分析依据和交付边界。
- M-3 → M-5：用户从免费报告进入付费升级。
- M-5 → M-3：支付验证通过后回到原报告页解锁深度内容。

### 6.3 信息架构

```text
首页 /
├── 产品价值、分析框架和公开案例
├── URL、网站目标和目标用户输入
├── 免费/付费报告对比
└── 方法论、隐私和条款入口

分析 /analyze
└── 分析阶段、进度、失败原因和重试入口

报告 /report/{id}
├── 免费报告
├── Evidence Layer
├── Action Plan
├── 邮箱保存
├── Deep Growth Report 购买入口
└── 付款确认后的深度报告

公开案例 /teardowns
├── 案例列表
└── 单个案例详情

辅助页面
├── /pricing
├── /privacy
└── /terms
```

### 6.4 核心数据模型

| 业务对象 | 核心属性 | 关联对象 | 关系类型 |
|---|---|---|---|
| AnalysisRequest | id、url、normalized_host、goal、audience、status、stage、timestamps、error_code | SourceSnapshot、Report | 一对一、一对多 |
| SourceSnapshot | title、meta、headings、schema、cta_candidates、evidence、content_hash、artifact_path | AnalysisRequest | 多对一 |
| Report | id、analysis_id、tier、score、pillars、issues、rewrites、action_plan、model、prompt_version | PaymentIntent | 一对零或一 |

## 7. 用户流程

### 7.1 核心流程

#### Flow-1：免费分析

**覆盖模块**：M-1 → M-2 → M-3 → M-4

**涉及功能**：F-1、F-2、F-3、F-4、F-6

| 步骤 | 用户操作 | 系统响应 | 涉及功能 |
|---:|---|---|---|
| 1 | 进入首页 | 展示价值主张、分析框架和 URL 输入 | F-1、F-6 |
| 2 | 输入 URL 和主要网站目标 | 校验协议、主机名和目标字段 | F-1 |
| 3 | 提交分析 | 创建 AnalysisRequest，进入 `/analyze` | F-1 |
| 4 | 等待分析 | 展示抓取、标题检查、信任检查和建议生成状态 | F-2、F-6 |
| 5 | 系统访问公开首页 | 采集结构化页面证据和截图 | F-2 |
| 6 | 查看免费报告 | 展示总体方向性评估、3 个核心问题和证据 | F-3 |
| 7 | 查看行动建议 | 展示 Quick Wins 和优先级 | F-4 |
| 8 | 可选保存报告 | 收集邮箱并发送报告链接 | F-12 |

#### Flow-2：付费 Deep Growth Report

**覆盖模块**：M-3 → M-4 → M-5 → M-3

**涉及功能**：F-3、F-5、F-6、F-11、F-12

| 步骤 | 用户操作 | 系统响应 | 涉及功能 |
|---:|---|---|---|
| 1 | 阅读免费报告 | 展示免费与付费内容差异 | F-3、F-6 |
| 2 | 点击升级 | 展示完整诊断、重写和行动计划 | F-11 |
| 3 | 提交邮箱 | 创建 PaymentIntent | F-12、F-11 |
| 4 | 跳转结账 | 创建 Pancake Checkout Session | F-11 |
| 5 | 完成支付或取消 | Pancake 返回 SiteLens | F-11 |
| 6 | 接收 Webhook | 验证签名、环境、商品、金额、币种和报告归属 | F-11 |
| 7 | 等待确认 | 支付成功前显示 pending，不提前解锁 | F-11 |
| 8 | 支付确认 | 创建 DeepReport 并更新 PaymentIntent | F-11 |
| 9 | 返回原报告 | 解锁完整问题清单、改写和页面结构 | F-5、F-11 |

#### Flow-3：失败与中断恢复

**覆盖模块**：M-1、M-2、M-3、M-5

| 场景 | 系统行为 | 用户操作 |
|---|---|---|
| URL 无效 | 阻止提交并显示格式错误 | 修正 URL |
| 网站无法访问 | 标记分析失败并显示失败阶段 | 重新提交 |
| 抓取或模型超时 | 不生成假报告，保留错误摘要 | 重试 |
| 用户关闭分析页 | 任务继续执行，报告链接可恢复 | 重新打开链接 |
| 用户取消支付 | PaymentIntent 标记 canceled | 回看免费报告或再次支付 |
| 支付成功但未返回 | Webhook 仍更新支付状态 | 重新打开原报告 |
| 返回成功但 Webhook 延迟 | 显示等待确认，不解锁 | 等待轮询完成 |
| 商品/金额/签名不匹配 | 拒绝自动解锁并记录异常 | 联系支持或人工处理 |

### 7.2 状态流转

**AnalysisRequest 状态流转：**

```text
draft → queued → fetching → extracting → analyzing → completed
                                      ↘ failed → retry(new request)
```

**PaymentIntent 状态流转：**

```text
created → checkout_opened → pending → paid → deep_report_ready
                              ↘ canceled
                              ↘ failed
paid → verification_failed → manual_review
```

| 从 | 到 | 触发条件 | 操作者 |
|---|---|---|---|
| draft | queued | 用户提交合法 URL | 用户/系统 |
| queued | fetching | Worker 领取任务 | 系统 |
| fetching | extracting | 页面访问成功 | 系统 |
| extracting | analyzing | 证据提取完成 | 系统 |
| analyzing | completed | 报告通过结构校验 | 系统 |
| analyzing | failed | 超时、抓取失败或模型失败 | 系统 |
| created | checkout_opened | Checkout Session 创建成功 | 系统 |
| checkout_opened | pending | 用户进入结账 | 用户/系统 |
| pending | paid | Webhook 验签和订单校验通过 | 系统 |
| pending | canceled | 用户取消或离开结账 | 用户/系统 |
| paid | deep_report_ready | 深度报告生成成功 | 系统 |

### 7.3 异常路径

| 场景 | 触发条件 | 用户看到什么 | 可执行操作 |
|---|---|---|---|
| 输入校验失败 | 协议、主机名或目标缺失 | 明确的字段错误 | 修正后提交 |
| SSRF/保留地址 | URL 指向私网、回环或元数据地址 | 无法分析该地址 | 更换公开网站 |
| 页面抓取失败 | 超时、反爬、登录墙 | 失败阶段和原因 | 重试或提交其他 URL |
| 页面内容不完整 | JS、图片或部分资源不可访问 | 可用证据与未知信息分开 | 继续查看有限报告 |
| 邮箱提交失败 | 格式错误或服务异常 | 邮箱错误或稍后重试 | 修正/跳过 |
| 支付失败 | Pancake 返回失败 | 不会解锁报告 | 重试或联系支持 |
| Webhook 重复 | 相同事件重复到达 | 用户无感知 | 由事件 ID 幂等处理 |

## 8. 功能详细设计

### M-1：分析入口

#### F-1：网站目标与用户上下文

- **功能描述**：收集公开网站 URL、网站主要目标和目标用户。
- **来源 JTBD**：JTBD-1、JTBD-2、JTBD-3。
- **输入**：URL；目标枚举；可选目标用户描述。
- **输出**：标准化 URL、目标和 AnalysisRequest ID。
- **交互说明**：URL 是首页主输入；目标为必选；目标用户可用一句话补充。
- **业务规则**：只允许 HTTP/HTTPS；禁止用户凭据、危险协议和受限地址；目标会写入报告上下文。
- **异常处理**：格式错误、私网地址、超长输入和重复提交均给出可操作提示。
- **关联功能**：依赖 F-2 的证据提取；驱动 F-3 的分析维度。
- **约束条件**：不要求先注册账号。

#### F-12：报告保存与邮箱交付

- **功能描述**：用户看到免费报告价值后，可提交邮箱保存报告或接收支付凭证。
- **来源 JTBD**：JTBD-2、JTBD-3。
- **输入**：邮箱、报告 ID、同意状态。
- **输出**：报告链接或交付确认。
- **业务规则**：不强制邮箱才能查看免费报告；记录同意时间；不保存支付卡信息。
- **异常处理**：邮箱格式错误、重复提交和交付失败可重试。

### M-2：页面证据引擎

#### F-2：页面证据提取

- **功能描述**：抓取公开首页并提取可解释的页面事实。
- **来源 JTBD**：JTBD-1、JTBD-3。
- **输入**：标准化 URL 和分析上下文。
- **输出**：标题、Meta、Heading、可见文本、CTA 候选、图片 alt、Schema、链接摘要和截图。
- **交互说明**：分析页按阶段展示进度；不向用户展示内部工具细节。
- **业务规则**：限制跳转次数、响应体大小、资源数量和总时长；页面内容视为不可信数据，不能改变系统指令。
- **异常处理**：部分资源失败时保存可用证据并标记 unknowns；主页面失败则任务失败。
- **关联功能**：为 F-3、F-4、F-5 提供输入。

### M-3：报告与行动计划

#### F-3：Evidence Report

- **功能描述**：把页面证据转成用户可以理解的转化诊断。
- **来源 JTBD**：JTBD-1、JTBD-3。
- **输入**：SourceSnapshot、网站目标、目标用户。
- **输出**：总体方向性评估、三项核心问题、证据、影响、修复建议、优先级、置信度和未知信息。
- **报告结构**：
  1. Executive Summary。
  2. Biggest opportunity。
  3. Top Issues。
  4. Evidence Layer。
  5. Quick Wins。
  6. 付费报告入口。
- **业务规则**：每个问题必须包含 Problem、Why it matters、Evidence、How to fix；不能只输出抽象建议。
- **评分规则**：评分是方向性评估，必须附依据；不展示没有来源的行业平均值。
- **异常处理**：证据不足时明确显示 unknowns，不把未知内容写成负面事实。

#### F-4：优先行动计划

- **功能描述**：将问题排序为最值得先做的三项行动。
- **来源 JTBD**：JTBD-2。
- **输入**：问题、影响、实施工作量、网站目标。
- **输出**：行动名称、预期影响、工作量、建议顺序和完成标准。
- **业务规则**：优先级以网站目标为上下文；不承诺具体转化提升比例。

#### F-5：Copy & Structure Rewrite

- **功能描述**：为 Hero、产品描述、CTA 和首页结构生成可直接参考的改写。
- **来源 JTBD**：JTBD-2。
- **输入**：页面原文、目标用户、网站目标、对应问题。
- **输出**：原文、问题、建议文案、替代版本和结构顺序。
- **业务规则**：改写必须基于页面信息；无法判断的业务事实不能编造。
- **异常处理**：上下文不足时标记需要用户补充，而不是填入虚构卖点。

### M-4：信任与报告交付

#### F-6：Trust Layer

- **功能描述**：解释 SiteLens 如何分析、分析了什么、没有分析什么。
- **来源 JTBD**：JTBD-3。
- **输入**：分析阶段、Growth Framework、证据和 unknowns。
- **输出**：分析过程、方法论、边界、置信度和公开 Teardown 入口。
- **Growth Framework**：Positioning、Clarity、Trust、Conversion、Authority。
- **业务规则**：不宣传替代人工增长顾问；不承诺转化率结果；不把 AI 作为唯一价值。

### M-5：付费报告

#### F-11：Deep Growth Report 购买与解锁

- **功能描述**：让用户购买一次性 $29 深度报告，并在支付验证后解锁完整内容。
- **来源 JTBD**：JTBD-2、JTBD-3。
- **输入**：报告 ID、邮箱、商品 ID。
- **输出**：Pancake Checkout Session、PaymentIntent、DeepReport。
- **业务规则**：生产环境商品为 `PROD_28rexkec6xEqGx2QMHEcJi`；支付必须验证签名、环境、商品、金额 USD $29、报告归属和事件幂等性。
- **异常处理**：取消、失败、Webhook 延迟、重复事件和校验失败均不自动解锁。
- **安全要求**：SiteLens 不接收或保存完整卡号；Waffo 私钥和 Webhook 公钥只存在服务端 Secret。

## 9. 非功能需求

### 9.1 性能要求

以下是 Beta 阶段建议值，需通过真实数据校准：

- 首页首屏：现代桌面和移动网络下目标小于 2.5 秒。
- 分析状态页：提交后立即返回，不同步等待完整抓取。
- 分析完成时间：目标 p50 小于 60 秒、p95 小于 120 秒。
- 付费接口：创建 Checkout Session 的正常响应目标小于 5 秒。
- Beta 并发：先以 10 个并行分析任务作为压测起点，不把它当成长期容量承诺。

### 9.2 安全要求

- 全站 HTTPS。
- URL 抓取必须阻止 loopback、私网、link-local、云元数据、IPv6 保留地址和 DNS 重绑定绕过。
- 限制协议、端口、跳转次数、响应体大小、资源数量和任务时长。
- 不携带用户 Cookie、Authorization、内部代理头或服务器环境变量。
- 将网页内容视为不可信输入，隔离网页 prompt injection。
- 公共接口限流，分析和支付请求具备幂等保护。
- Waffo Webhook 验签，支付返回页不能单独证明付款成功。
- 原始 HTML、截图和报告按最短业务需要保存，并提供删除机制。
- 支付私钥、AI Key 和 Webhook 公钥不进入客户端、Git 或报告内容。

### 9.3 兼容性要求

- 支持现代 Chrome、Edge、Safari 和 Firefox。
- 支持桌面端和至少 390px 宽度的移动端。
- 报告在浅色和深色系统设置下均可阅读。
- 不依赖用户网站的特定框架或 CMS。

### 13.2 调研记录

- 直接竞品普遍采用 URL 分析、评分、问题优先级和付费报告模式。
- “AI 分析”“截图”“评分”“CTA 建议”本身不是足够差异化。
- 第一主线应聚焦有公开 SaaS 首页、且目标是注册或 Demo 的创业者。
- 产品保持宽入口，但通过网站目标字段适配小企业和其他网站。
- 先验证一次性 Deep Growth Report，不提前做订阅和企业级工作区。

### 13.4 术语表

- **Growth Framework**：SiteLens 的五步分析框架：Positioning、Clarity、Trust、Conversion、Authority。
- **Evidence Layer**：每条建议对应的问题、影响、页面证据、修复方式和改写方向。
- **Deep Growth Report**：一次性付费的完整诊断报告，价格为 $29。
- **Unknowns**：页面或抓取过程无法确认的信息，必须与事实和推断区分。
- **JTBD**：Jobs-to-be-Done，用户希望完成的核心任务，而不是产品功能。
- **P0/P1/P2**：分别表示验证核心价值、增强购买和传播、长期平台化能力。
